# Beyond Clarification Counts — replication materials

Replication materials for *Beyond Clarification Counts: An Exploratory Study of User Story Clarification in Spec-Driven Development*.

## Study and scope

The study examines questions generated by Codex using a noninteractive adaptation of GitHub Spec Kit's clarification instructions. It contains 45 prepared parent stories (25 Zooniverse, 10 PlanningPoker, and 10 BADCamp), each with a baseline and syntactic, semantic, and pragmatic perturbations: 180 inputs and one execution per input.

Baselines are within-story comparators, not certified defect-free requirements. The perturbation profiles describe intended changes rather than independently validated diagnoses of all 135 variants; ten pragmatic variants have no finalized mapping to an individual QUS criterion. Prepared stories can omit source context, including benefit clauses.

The research questions address observed counts, the content of selected questions, and illustrative matched traces. The study does not estimate defect-detection accuracy or evaluate stakeholder answers, completed interactive clarification, or downstream software.

## Released results

Recounting the tagged items in `results_new/*/final_response.md` reproduces the manuscript totals:

| Condition | Tagged items | Executions at the five-question limit |
|---|---:|---:|
| Baseline | 224 | 44 |
| Syntactic | 221 | 43 |
| Semantic | 224 | 44 |
| Pragmatic | 225 | 45 |
| **Total** | **894** | **176** |

Counts are unchanged in 131 of 135 baseline–variant comparisons. The five-question ceiling limits interpretation: equal counts cannot establish whether an intended defect was explicitly raised.

Two specialists reviewed 100 selected questions by consensus: 76 concerned requirement meaning or scope and 24 requested operational details. The sample contains 25 questions per condition, from 77 executions and 39 parent stories. Selection was intentional, not random, and does not support prevalence estimates for all 894 items. No blinded independent coding or inter-rater reliability estimate is claimed.

`reference/final_classification.csv` retains the original labels: **Classical Normative Scope** corresponds to the manuscript's **requirements concerns**, and **Extended Scope (New AI Dimension)** corresponds to **operational detail**. The latter name does not establish that these information needs are specific to AI. Historical provisional notes remain part of the provenance; the documented subsequent human consensus identifies the final labels.

## Execution protocol

The 180 recorded executions took place on October 14, 2026, using Codex CLI configured with model alias `gpt-6.1-sol`. Each case used a separate workspace, the same clarification skill and constitution, and a minimal active specification. The runner used a read-only sandbox and JSON event logging, without explicit temperature or decoding settings.

The adapted prompt requested up to five numbered questions in a single response, each followed by `[NEEDS CLARIFICATION: specific risk]`. It prohibited stakeholder replies, recommended answers, file modification, and implementation. This is question generation under an adapted protocol, not Spec Kit's full interactive workflow. The model alias is not an independently resolved backend snapshot.

## Inspecting and reproducing

Existing outputs can be inspected without rerunning the model. From the repository root:

```powershell
python run_replication.py --help
python run_replication.py --all --dry-run
```

To extract the released raw markers:

```powershell
python extract_markers.py
```

The extraction writes `markers_for_review.csv` without invoking the model. Its rows retain preceding response context rather than claiming to be cleanly parsed or independently validated questions.

New executions require a compatible Codex CLI and access to the configured model. Model execution may incur costs and need not reproduce identical responses. The runner skips cases with completion markers and refuses to overwrite existing case directories without them. Use a separate copy for new runs and preserve the released results.

The original experimental hashes identify original files; sanitized release copies have separate hashes in the release manifest. Private original logs and pre-release Git history are not included. Historical preparation notes describe the state when recorded and should be read with subsequent confirmation entries.
